# Upstream: Wave Terminal

Moltenterm is a soft fork of [Wave Terminal](https://github.com/wavetermdev/waveterm) (Apache-2.0, Command Line Inc.).
This file explains how the fork is built, how Wave releases are merged, and every place where Moltenterm changes Wave's
code.

## Toolchain

- Go 1.26.10, pinned by the `go` line of `go.mod` (updated for security maintenance in #810 and #941) or, if a
  newer one is ever needed, by a `toolchain` line (`go mod tidy` drops one equal to the `go` line). CI reads it through
  `go-version-file: go.mod`. Those lines are only a minimum for Go, so a newer local Go (Homebrew's) would build as is; the Taskfile therefore exports
  `GOTOOLCHAIN=<that version>` (`scripts/moltenterm-go-toolchain.mjs`), and `go` fetches and runs exactly that
  toolchain. `build:backend` and its quickdev variants, `task check:go` and CI's Backend job fail when `go` runs
  another version, and `scripts/moltenterm-build-gold.sh` prints the version and stops on a mismatch. Run raw `go`
  commands inside the repository with `GOTOOLCHAIN=$(node scripts/moltenterm-go-toolchain.mjs)` to match. To move the
  pin, change `go.mod`'s `go` line (`go mod edit -go=1.x.y`): CI, Task and the gold follow. Task v3, Node 22 with npm 10.9.2, and Zig for the CGO builds
  on Linux and Windows. On macOS, the Xcode Command Line Tools are also required.
- macOS setup: `brew install go go-task`, Node 22 through nvm or Homebrew.

| Command                                    | What it does                                                                                                       |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `task init`                                | Install the npm dependencies (app and docs site) and tidy the Go modules. Run once, then after dependency changes. |
| `task dev`                                 | Run the app through the Vite dev server (renderer hot reload). Uses `waveterm-dev` directories.                    |
| `task start`                               | Run the app without the dev server.                                                                                |
| `task package`                             | Build a distributable for the current platform into `make/`.                                                       |
| `task check:ts`                            | Type-check the frontend and Electron code.                                                                         |
| `npx vitest run`                           | Frontend unit tests.                                                                                               |
| `go test ./cmd/... ./pkg/...`              | Backend tests.                                                                                                     |
| `task generate`                            | Regenerate TypeScript bindings after changing Go RPC types.                                                        |
| `node scripts/moltenterm-check-ledger.mjs` | Check the patch ledger against the last merged Wave release.                                                       |

Test instances (CI, worktree agents, scripted runs of the built app) start with `MOLTENTERM_SKIP_ONBOARDING=1` unless
the test is about the first run: the first run is recorded as done and the first tab gets Wave's starter layout, as
before #161. wavesrv reads the variable once and removes it from its environment, so terminals of that instance do not
pass it on; `1` and `true` (any case) skip, any other value does not.

Test instances also start with `MOLTENTERM_BACKGROUND=1` (#495), so that they never take the keyboard focus or cover
the user's windows; only `1` turns it on, and without it nothing changes. On macOS the instance runs with the
`accessory` activation policy (no Dock icon, no menu bar, never the active app); every window is shown with
`showInactive()`, keeps its size and is parked in the bottom-right corner of the primary display with only 160 by 120
points on screen, floating above the other windows on every Space so that they never cover it (an entirely covered
window counts as occluded: its pages go `hidden` and stop drawing), transparent and click-through so that the corner
stays the user's. A locked screen still hides every page. Focus is virtual: the window the app focuses
reports `isFocused()`, is the one `getFocusedWindow()` returns and gets its `focus` event, while the OS focus stays with
the user's app; `webContents.focus()` (which would activate the app) only runs in a window the user clicked. Drive the
pages through CDP, whose input reaches a page whatever the OS focus, and use `Emulation.setFocusEmulationEnabled` when a
page must believe it has the focus. A launch for a manual test plan:

```sh
MOLTENTERM_BACKGROUND=1 MOLTENTERM_DATA_HOME=/tmp/mtNNN/d MOLTENTERM_CONFIG_HOME=/tmp/mtNNN/c \
  WAVETERM_NOCONFIRMQUIT=1 MOLTENTERM_SKIP_ONBOARDING=1 ./node_modules/.bin/electron . --remote-debugging-port=9NNN &
```

The perf harness (`scripts/perf/`) launches every instance this way unless `run --foreground`.

## Local builds and their signature

`scripts/moltenterm-build-gold.sh` builds the gold (Mission Control's Gold build in `.molten/project.json`) and delivers
it where the installed gold looks for updates. It signs the app and every nested helper, framework and binary with the
code-signing identity "MoltenTerm Local" (`MOLTENTERM_SIGNING_IDENTITY` overrides the name), with the entitlements and
hardened runtime of `electron-builder.config.cjs`. macOS then knows every gold by
`identifier "fr.diamondforge.moltenterm.gold" and certificate leaf = H"…"`, the same from one build to the next, so the Files
and Folders and Full Disk Access grants carry over (#224). Ad hoc, a build is known by its cdhash, and the grants given
to one gold stop applying to the next while System Settings still shows them as allowed.

Create the identity once per Mac, from a terminal, and accept the two prompts (trust the certificate for code signing,
then "Always Allow" codesign to use its key):

```bash
./scripts/moltenterm-local-signing-identity.sh
```

It reuses a valid identity of that name, and trusts one an earlier run imported but left untrusted. The certificate is
self-signed, valid ten years, and its private key never leaves the login keychain. The build only checks the identity
(`--check`, read-only); without it, the build warns and signs ad hoc. `--name <identity>` makes the script usable by any
other standalone app. Check a gold with `codesign -d -r- "/Applications/MoltenTerm Gold.app"`. The first signed gold
replaces an ad hoc one, so its grants must be given once more; they hold from then on.

**What an installed gold accepts as an update (#663).** The gold folder is writable by any process of the user, so the
installed gold takes a new build only when `codesign --verify --deep --strict -R=<its own designated requirement>`
passes on the bundle in the gold folder and again on the staged copy (`emain/moltenterm-gold-signature.ts`): the same
identifier and the same "MoltenTerm Local" certificate leaf, every nested helper sealed. An ad hoc signature names no
identity and is refused. The swap script verifies the staged copy once more right before swapping, and only then
removes its quarantine. An installed gold ignores `MOLTENTERM_GOLD_DIR` (it is for the delivery script and unpackaged
test runs). Consequences: a gold signed ad hoc refuses every update; install one gold signed with the local identity
by hand (build it after running `scripts/moltenterm-local-signing-identity.sh`, then copy it from the gold folder to
`/Applications`), and updates flow from then on. Recreating the identity (a new certificate) is the same: the next gold
is installed by hand once.

**The gold and releases on one Mac (#509).** A release keeps the product's identity: bundle identifier
`fr.diamondforge.moltenterm`, data in `~/Library/Application Support/moltenterm`, configuration in
`~/.config/moltenterm`. The gold has its own, as dev builds do: `fr.diamondforge.moltenterm.gold` (`-c.appId` in the
gold script, `GoldIdentifier`), `moltenterm-gold` folders, and so its own single-instance lock and Chromium profile
(`<data>/electron`). Both run at once without sharing anything, and granting a release Full Disk Access or Files and
Folders never replaces the gold's grants (macOS keeps one entry per bundle identifier). The first gold with this
identity was installed by hand (the delivery printed how: the installed gold refuses a gold with another identifier),
renamed the old `moltenterm` folders to `moltenterm-gold` on its first start (refusing to while another MoltenTerm held
them), and needed its grants once more. `RELEASE.md` has the release checklist.

## Continuous integration

Local Vitest and ESLint discovery excludes `.claude/worktrees/**` relative to the checkout root (#820), while
retaining framework defaults and the rest of the harness and workspace scope. A checkout located inside that
directory still validates its own files. Run `node --test scripts/moltenterm-worktree-discovery.node-test.mjs` to verify
both ignored nested failures and detected current-checkout failures with isolated disposable fixtures.

`.github/workflows/ci.yml` runs on every pull request to `develop` or `main` and on every push to them.

| Job           | When                              | Steps                                                                                                                                         |
| ------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Quick checks  | Always, drafts included           | `node scripts/moltenterm-check-ledger.mjs`, `node scripts/moltenterm-check-icons.mjs`                                                         |
| Dependency security | Always, drafts included | Reusable secret-free `security-scan.yml`: pinned npm/govulncheck, both module graphs and declared targets, scoped policy verdict and raw evidence artifact |
| Frontend      | Skipped on draft pull requests    | `npm ci`, `npx tsc --noEmit` (the command behind `task check:ts`), `npx eslint . --quiet`, `npx vitest run`, `npm run build:prod`             |
| Backend       | Skipped on draft pull requests    | `node scripts/moltenterm-go-toolchain.mjs --check`, `go test ./cmd/... ./pkg/...`, `task build:backend` (Linux; wavesrv's CGO build uses Zig) |
| Perf budgets  | Skipped on draft pull requests    | Builds the app and runs `node scripts/perf/perf.mjs run --profile ci --gate ci` under Xvfb (bundle, JS evaluated, start-up, leaked views); posts the report on the pull request (`scripts/perf/README.md`) |
| Required gate | Always, from the start of the run | Requires Quick checks and Dependency security success, plus Frontend, Backend and Perf budgets success (skipped only on a draft) |

Marking a draft pull request ready for review starts the full run, and returning it to draft cancels that run.
"Required gate" is the one check a branch ruleset should require. It starts with every run and polls the other jobs
instead of waiting for them through `needs`, so its check is pending from the first second: a pull request just marked
ready cannot satisfy the ruleset with its draft's result while the full run is still going. Run the same commands
locally before pushing: the ledger check reads the working tree, so it also sees uncommitted changes.

The same dependency security workflow gates release packaging and publication; release runners also scan their native
CGO-enabled Go source before packaging. `dependency-security.yml` adds a weekly/manual scan without release credentials.
See `security/README.md` for coverage, exit states and the exact advisory review/expiry policy (#810).

`.github/workflows/pr-review-sync.yml` comes from the SaaSFoundryAI harness, with one local change (#709): its
`sync-review` job runs only for ticket branches (`feature/{N}-…`, `fix/{N}-…`) and is skipped for the others, such as
release sync-backs and `rc-*` branches, which have no ticket to sync. Keep this change when a harness update rewrites
the file, until the harness ships it. It runs from the default branch (`pull_request_target`), so it takes effect once
it reaches `main`.

## Releases

Releases are cut from Mission Control (Project tab › Release, then each step on its click in the release panel) or
from a terminal with the same commands. The steps are `release.rc` and `release.public` in `.molten/project.json`; they
call the generic `molten release` commands ("Generic release commands" in `pkg/molten/agentdocs/pipeline-format.md`).
Release candidates are `v1.0.0-N` until the first public release, `v1.0.0` (FR-REL-001).

| Phase   | Step                                               | What happens                                                                                                                                                                                                 |
| ------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| prepare | `molten release promote --workflow ci.yml`         | `develop` reaches `main` (fast-forward, else a merge commit) once CI is green on its commit. Refused while `main` holds a release commit `develop` lacks: merge the previous sync-back first.                |
| prepare | `molten release prepare <tag>`                     | In `../MoltenTerm-release` (a worktree on `origin/main`): `package.json` and `package-lock.json` bumped, `releases/<tag>.md` and `releases/<tag>.internal.md` written ("Release notes", below). Review the notes before the cut. |
| cut     | `molten release finalize <tag>`                    | Commit `chore(release): <tag> (rc\|public)`, tag, `git push --atomic origin main <tag>` (as a repository admin: the `main` ruleset accepts pull requests only).                                              |
| build   | `.github/workflows/release.yml`                    | On the tag: macOS arm64 and x64 (dmg, zip; public tags require Developer ID, notarization and final delivery verification) and Linux x64 and arm64 (AppImage, deb), checked to come from `main` and carry the tag's version. |
| publish | release.yml, then `molten release close-milestone` | The GitHub release with every file, `SHA256SUMS.txt` and electron-builder's `latest*.yml`: a candidate is published as a prerelease, a public release waits as a draft. Its milestone closes once published. |
| back    | `molten release sync-back <tag>`                   | The release commit cherry-picked onto `develop` in `chore/sync-back-<tag>`, with its pull request.                                                                                                           |

**Rehearsal (no tag, no release).** Before cutting a release candidate, build its files from `develop` and install
them: Mission Control › CI/CD › CD › "Rehearse the release build", or from a terminal
`molten release rehearse --workflow release.yml [--download <folder>]`. It dispatches `release.yml` on `develop`
(`gh workflow run release.yml --ref develop [-f channel=public]` by hand), which then runs the same macOS and Linux
jobs as a tag, checks the same file set (`scripts/moltenterm-release-files.sh`), skips the publish job and keeps the
files as artifacts `moltenterm-rehearsal-<os>-<sha>` with `SHA256SUMS.txt` for 14 days. The build is stamped with
`package.json`'s version on the `rc` channel (or `public`). The step waits for the run, lists the artifacts and
downloads them into `~/Downloads/MoltenTerm-rehearsal/<short sha>/`; run again on the same commit, it reuses the
rehearsal instead of building again. GitHub only dispatches a workflow it knows: until `release.yml` is on `main`, it is
known because a pull request that changes it runs its first job (check mode, nothing built).

The release needs nothing more on GitHub than the repository's own token (`contents: write` for the publish job only)
and, to be signed, the two secrets of the release key (#576): `scripts/moltenterm-release-sign.sh` signs
`SHA256SUMS.txt` into `SHA256SUMS.txt.asc` (plus a `.asc` per AppImage and deb) on a release and a rehearsal, verified
against the committed `release-signing-key.asc` (fingerprint `A2E8049BB69F46620E99C304B003BEB5DC25CABA`). Public tags
fail when either signing system is absent (#976); candidates and rehearsals retain optional checksum signing, and
partial or invalid material always fails. Rehearsals remain ad hoc. Public packaging verifies extracted ZIP apps and
read-only mounted DMG apps, then records final macOS hashes in `macos-verification.json`. Publication validates the
exact inventory, feeds, blockmaps, evidence and signatures before any mutation. Existing published releases are
immutable, as are existing draft assets: a rebuild with different bytes or run evidence is refused and requires explicit repair. Public releases
still wait as drafts for human publication; clean-computer/offline/CLI/permission acceptance remains #880. Windows
builds come later.

**Telling users about a new release (#188).** There is one update source, the repository's GitHub Releases, read with
no feed file of its own. A release build (`rc` or `public` channel) asks the Releases API once its window is idle after
start, and again when a window gets the focus, but at most once a day (an hour after a failed request), anonymously
from a session of its own. The releases read are kept in `<data>/molten/update/release-check.json`, and the offer is
picked from them at every answer for the version running then and the release candidates preference, so an installed
update or a change of the preference never shows a stale offer. The setting `moltenterm:releasecandidates` (Settings ›
General › Updates, "Also get release candidates", off by default, #948) alone decides, whatever build was installed
first: off, only public releases newer than the build are offered (a candidate install moves to the next public release,
never an older one); on, the next candidate or public release, whichever is newer. The build's channel only decides
whether it looks at all. A newer release shows once in the notification center ("MoltenTerm X
is available", its public notes up to the release body's `## Install` heading, a Download button to its github.com
release page), one window announcing it for all, and as a status bar entry that opens the page; a release no longer
offered is withdrawn. The setting `moltenterm:releasenotify` turns it off. Golds (local update, #64) and dev or local
builds never ask. Nothing is downloaded or installed, and Wave's auto-updater stays off (#5): installing from the app
needs signed builds (#507, follow-up #536). A test instance (`MOLTENTERM_BACKGROUND=1`) can point the check at a feed on
this machine with `MOLTENTERM_RELEASE_FEED_URL=http://127.0.0.1:<port>/…`. Wave's `RELEASES.md` describes Wave's own process and does not apply.

### Release notes

Every release has two files in `releases/`, committed with the version bump by `molten release finalize` (FR-REL-003).
The paths come from `versions.notes` in `.molten/project.json` (`releases/{tag}.md`), so any project using the
generic commands gets the same pair.

| File                          | Who reads it | Where it goes                                                                                                              |
| ----------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `releases/<tag>.md`           | users        | The GitHub release body (`release.yml`, before the install text), the app's version history (bundled at build time), the update notification. |
| `releases/<tag>.internal.md`  | developers   | Nowhere but the repository: every ticket of the range with its title and link, the commits claiming no ticket, the diff link. Never bundled. |

`<tag>` is the full tag: `v1.0.0-3` for a release candidate, `v1.0.0` for a public release. The public file is markdown
with an optional front matter, `key: value` lines between two `---` lines:

```markdown
---
date: 2026-10-20
draft: true
---

## What this version brings

One short paragraph, then at most three `###` sections.
```

- `date`: the day of the cut, written by `molten release prepare`.
- `draft: true`: notes written ahead of the cut that are not ready. `molten release finalize` refuses them, `release.yml`
  fails on them, and the app's version history leaves them out. Remove the line once the notes are final.
- Any other key is kept and ignored. Readers show the markdown after the front matter: `scripts/moltenterm-release-notes-body.mjs`
  (what `release.yml` uses), `pkg/molten/release/notes_format.go`, and the app's catalog in `frontend/moltenterm-shell/releases`.

The public text must pass the audit (`molten release notes <tag> --check`, also run by finalize): no ticket reference
(`#123`), no link into the repository, no commit or ticket count, at most 25 non-empty lines.

How the notes are written, during `molten release prepare <tag>`:

1. The facts: the conventional commits since the previous release (the last public one for a public release, the last
   of either channel for a candidate), the tickets they claim and the closed issues of the version's milestone.
2. The engineering record is derived from them, with no agent.
3. The public notes are written by the coding agent CLI named in `versions.notesagent` (MoltenTerm: `claude -p` with its
   tools disabled; Codex is `["codex", "exec", "-"]`), the prompt on its standard input, audited; after two refused or
   failed attempts, or with `MOLTEN_RELEASE_NOTES_AI=off`, they are the `feat` subjects under New and the `fix`, `perf`
   and `revert` ones under Fixed. `MOLTEN_RELEASE_NOTES_AGENT="codex exec -"` replaces the agent for one run.
4. Notes already on `main` (written by hand, like `releases/v1.0.0.md`) are kept: prepare only stamps their `date` and
   warns about a `draft: true` line or what the audit finds.

Review them before the cut: in Mission Control, the release panel edits the file and "Rewrite" runs the
`rewrite-notes` step (`molten release notes {tag}`); in a terminal, `molten release notes <tag>` rewrites them and offers
accept, edit (`$EDITOR`), redo, plain (from the commit subjects) or quit. The cut (finalize) is the acceptance.

## Remotes, once per clone

```bash
git remote add upstream https://github.com/wavetermdev/waveterm.git
git config remote.upstream.tagOpt --no-tags          # never fetch Wave's tags
git remote set-url --push upstream NO_PUSH_TO_UPSTREAM
git config rerere.enabled true                       # replay conflict resolutions
gh repo set-default DiamondForgeFr/moltenterm
```

`gh` resolves a remote named `upstream` before `origin`. Without `gh repo set-default`, ticket and pull request commands
(including the SaaSFoundryAI workflow scripts) silently target Wave's repository.

## Merging a Wave release

1. Open a ticket and a branch `feature/<N>-merge-wave-<version>` from `develop`.
2. Resolve the release commit: `git ls-remote --tags upstream refs/tags/<version>`, then `git fetch upstream main` (or
   `git fetch upstream <sha>` if the release is not on `main`).
3. `git merge --no-ff <sha>` and resolve conflicts with the policy below.
4. Check that no Wave automation came back: `git diff --name-status <sha> HEAD -- .github CNAME` must list only
   Moltenterm's own files. Delete any new Wave workflow, Dependabot or funding file.
5. Validate: `task init`, `node scripts/moltenterm-check-icons.mjs` (Wave targets Font Awesome Pro: any new Pro-only
   icon must get an alias in `public/moltenterm-icons.css`), `task check:ts`, `npx vitest run`,
   `go test ./cmd/... ./pkg/...`, then `task dev`.
6. Keep Moltenterm's `version` in `package.json` and `package-lock.json` on conflicts (never Wave's), and set
   `MoltentermWaveBaseVersion` in `pkg/wavebase/moltenterm_identity.go` and `frontend/util/moltenterm-identity.ts` to
   the merged release. Never run Wave's `task version` bumper: releases are numbered by `.molten/project.json`.
7. Update the "Current base" table, then the patch ledger until `node scripts/moltenterm-check-ledger.mjs` passes: it
   names every Wave file Moltenterm still changes without an entry or a marker, and every entry the new release made
   pointless.
8. Open the pull request to `develop` and merge it with a **merge commit**. Never squash or rebase: both drop Wave's
   history and make every later merge a conflict.

Never push Wave's tags: `git push` without `--tags`, and `tagOpt` keeps them out of the local repository.

## Merge methods

| Pull request                                 | Method                                                 |
| -------------------------------------------- | ------------------------------------------------------ |
| Moltenterm features and fixes into `develop` | Rebase or squash                                       |
| Wave release merges into `develop`           | Merge commit only                                      |
| Releases `develop` → `main`                  | Merge commit (or fast-forward), never rebase or squash |

Rebasing or squashing a branch that carries Wave's history rewrites its commits, and every later upstream merge then
conflicts. Never rebase locally a branch that contains an upstream merge. On `main`, a ruleset accepts changes through
pull requests only and allows merge commits only (repository admins can bypass it).

## Files Moltenterm owns

Mission Control local commands use a detached shell supervisor and an atomically published `completion` control
file alongside `run.json` and `output.log` (#812). Output is never lifecycle authority, including `exit=N` lines.
Restart recovery reads that control file; a legacy running record stays running while its process exists, then
becomes lost without a known result. Existing terminal history is retained. Build preparation records its known
result directly before handing execution to the same supervisor.

| Path                                                                                                               | Policy when merging                                                                                                                                   |
| ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CLAUDE.md`                                                                                                        | Keep ours. Re-sync its "Codebase conventions (upstream Wave)" section with upstream's `CLAUDE.md`.                                                    |
| `.gitignore`                                                                                                       | Union of both, but never ignore `.claude` (it holds the SaaSFoundryAI harness).                                                                       |
| `.github/`                                                                                                         | Keep ours. Delete any new upstream workflow, `dependabot.yml` or `FUNDING.yml`.                                                                       |
| `CNAME`                                                                                                            | Stays deleted: it points to Wave's documentation domain.                                                                                              |
| `README.md`, `NOTICE`                                                                                              | Keep ours. `NOTICE` must keep Wave Terminal's notice line. `README.ko.md` and `README.zh-TW.md` stay deleted.                                         |
| `public/fontawesome/`, `docs/static/fontawesome/`                                                                  | Stay deleted: Font Awesome Pro is not redistributable. If Wave adds or updates Pro files, delete them again and extend `public/moltenterm-icons.css`. |
| `LICENSE`                                                                                                          | Upstream's file (Apache-2.0).                                                                                                                         |
| `.claude/`, `.agents/`, `.saasfoundry.json`, `AGENTS.md`, `GEMINI.md`, `MANIFESTO.md`, `PRIVACY.md`, `UPSTREAM.md` | Moltenterm only; no upstream counterpart.                                                                                                             |

## Identity and rename procedure

Moltenterm's identity lives in a few places, so renaming the product is a short, mechanical change:

1. `frontend/util/moltenterm-identity.ts`: product names, window title, tagline, repository URL, directory base name and
   the `MOLTENTERM_*` override variables.
2. `pkg/wavebase/moltenterm_identity.go`: directory base name and repository URL for Go.
3. `package.json`: `name`, `productName`, `description`, `homepage`, `build.appId` (then `npm install
--package-lock-only`).
4. `build/moltenterm/`: `icon.svg` (source), `icon.png`, `icon.icns`, `deb-postinstall.tpl`; `public/logos/moltenterm-logo.png`;
   `frontend/app/asset/logo.svg`; `public/moltenterm-mark.svg` (CSS mask). The brand kit itself (symbol, lockups, app
   icons, colours) is `build/moltenterm/brand/`. The macOS icons (`icon.icns`, and `icon-gold.icns` for gold builds) are
   drawn on Apple's icon grid by `node scripts/moltenterm-gen-icons.mjs` from the kit's symbol.

The name is written MoltenTerm wherever people read it; identifiers keep the lowercase form (`moltenterm` directories,
`fr.diamondforge.moltenterm`, `MOLTENTERM_*`, the `molten` command). The gold folder keeps `Moltenterm Local Builds/…/
Moltenterm.app`, so golds installed before the rename keep recognising their updates.

Everything else (directories, lock, socket, menus, About panel, permission prompts) derives from these. Changing
`build.appId` or the directory name makes the OS treat the result as a new application, with fresh settings and data.

## Patch ledger

| Wave file | Change | Why | Ticket |
| --- | --- | --- | --- |
| `vitest.config.ts`, `eslint.config.js` | Exclude checkout-relative nested worktree storage, retaining default exclusions | Validate only the current checkout | #820 |

Terminal accessibility (#808, FR-SHELL-070) updates already-listed `frontend/app/view/term/termwrap.ts`,
`emain/emain-ipc.ts`, `emain/preload.ts`, `frontend/types/custom.d.ts`,
`frontend/preview/mock/preview-electron-api.ts`, `pkg/wconfig/settingsconfig.go`,
`pkg/wconfig/defaultconfig/settings.json`, generated settings schema/types/constants, and `docs/docs/config.mdx`.
The `moltenterm:terminalscreenreader` preference stays outside `term:*` so live changes never reconstruct xterm.
The new terminal-accessibility module binds only its public live option; main exposes read-only native detection.

Every change to a Wave file is listed here and, where the format allows comments, marked with `MOLTENTERM-PATCH` in the
file. Code that lives in new files is not listed.

`node scripts/moltenterm-check-ledger.mjs` enforces this against the release in "Current base". It fails when a

## Known upstream items

- **Font Awesome Pro 6:** resolved by #6 (FR-FORK-004). HEAD ships Font Awesome Free plus `public/moltenterm-icons.css`;
  the Pro files remain in Wave's history, which Moltenterm keeps (decision of 2026-09-29).
- **Wave branding left on purpose:** links to docs.waveterm.dev (still the only documentation of the configuration),
  `wsh` help texts, and pages that are no longer reachable (the opt-out "star us" page, release notes and upgrade
  modals). The `docs/` site is Wave's documentation (Algolia index, Plausible analytics); it is not built or shipped.
- **Built-in AI:** removed by #25 (FR-MORPH-008). Wave's AI code stays in the tree, unreachable: the panel is not mounted
  and never opens, its buttons, shortcuts, menu entry, tour page, tips, config entries and settings are gone, `wsh ai` is
  deleted, and the chat entry points refuse every request. The "Wave AI" strings left in that code are never shown, so
  the planned rename is dropped. The constants `MoltentermNoAI` (`frontend/util/moltenterm-noai.ts` and
  `pkg/aiusechat/moltenterm_noai.go`) mark every place that depends on it.
- **Identity:** resolved by #4 (FR-FORK-002). Still shared with Wave, on purpose or for later: `~/.waveterm` on remote
  hosts reached over SSH or WSL (WSL uses a fixed socket there), `~/waveapps` (app builder only), `TERM_PROGRAM=waveterm`
  (kept so that tools which detect Wave keep working), and the `WAVETERM_*` variables that hand directories to wavesrv.
  The version number is Moltenterm's own since #184 (FR-REL-001): `1.0.0-0` before the first release candidate, then
  `X.Y.Z-N` and `X.Y.Z`. The remote wsh keeps Wave's rule (same or newer is up to date), so while `~/.waveterm` is
  shared, a Wave wsh numbered above Moltenterm's would be kept; #192 moves Moltenterm to its own remote folder.
- **Outbound services:** resolved by #5 (FR-FORK-003). No update feed, no Wave cloud, no telemetry upload. Events are
  still recorded locally (dormant). #5's AI patches (user-defined modes only, "wave" modes refused) stay as a second
  line behind #25's refusal.
- **Baseline failures inherited from v0.14.5:** resolved by #7 (FR-FORK-005); still present on upstream `main` on
  2026-09-30. `task check:ts` reported 17 errors from three stale mocks in `frontend/preview/`, and `pkg/tsgen`
  `TestGenerateWaveEventTypes` expected a one-line `WaveEventName` union while the generator emits a multi-line one.
  Both fixes stay Moltenterm patches (decision of 2026-09-30: not offered upstream).
- **Default content:** the first-run layout opens a web block on Wave's GitHub page, and onboarding still links to
  Wave's GitHub and Discord. Addressed by #4 (the Wave AI panel no longer opens by default since #5). Since #161,
  Wave's onboarding (`frontend/app/onboarding/`) is no longer mounted: MoltenTerm's first run
  (`frontend/moltenterm-onboarding/`) replaces it, and Wave's starter layout only appears with
  `MOLTENTERM_SKIP_ONBOARDING`. Wave's `onboarding:lastversion` is no longer written; the client meta
  `molten:onboarding` records the first run.
- **`task dev` environment:** resolved by #5. The dev tasks no longer set `WCLOUD_*` (Wave's development cloud) or
  `WAVETERM_ENVFILE`, so the SRS token in `.env` stays out of the app.
